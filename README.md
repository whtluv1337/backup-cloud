# Облачная система управления резервными копиями

Учебный проект по НиАСПО. Тонкова Лана Владимировна, ИКБО-15-25.

## Что реализовано

Семь сервисов: proxy, frontend, api, worker, redis, repository, source. Ручное и периодическое резервное копирование (каждые 3600 секунд), список снимков, проверка всех данных репозитория, восстановление выбранной версии в ZIP, журнал состояний. Источник содержит только синтетические файлы. Используется restic 0.19.1 с шифрованием репозитория.

Поставляются отдельные конфигурации Docker Compose, Swarm и Kubernetes, пять Dockerfile и GitHub Actions CI/CD. Все три варианта развёртывания запущены и проверены 15.11.2026.

## Подтверждённые проверки

Пройдены 10 модульных тестов и полный HTTP-сценарий в Docker Compose (8080), локальном Swarm (8081), Kubernetes (8082) и Swarm на временной облачной ВМ GitHub Actions. Проверены отказ без токена, создание снимка, восстановление ZIP, содержимое трёх файлов, SHA-256 и полный restic check. Протоколы проверок сохраняются в артефактах GitHub Actions.

Kubernetes Docker Desktop: три логических узла Ready, девять подов Running и четыре PVC Bound. Локальный Swarm одноузловой. Эти результаты не доказывают устойчивость к потере физического компьютера или принудительное применение NetworkPolicy.

Запуски CI/CD: https://github.com/whtluv1337/backup-cloud/actions .

## Быстрый запуск на Windows

1. Установите и запустите Docker Desktop с Linux containers и WSL 2. Официальная инструкция: https://docs.docker.com/desktop/setup/install/windows-install/ . Может потребоваться включение виртуализации и перезагрузка. Эти системные действия выполняет владелец компьютера.
2. Установите Python 3.12 и Git, если они отсутствуют. Откройте терминал в этой папке.
3. Выполните:

```powershell
py scripts/init_secrets.py
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

4. Откройте http://127.0.0.1:8080 . Скопируйте токен из `secrets/api_token.txt` в поле интерфейса и нажмите «Подключиться».
5. Нажмите «Создать резервную копию». Дождитесь состояния «Завершено», выберите снимок, нажмите «Восстановить» и скачайте ZIP из журнала.
6. Нажмите «Проверить хранилище» и дождитесь завершения.

Пароль `secrets/restic_password.txt` нужен для расшифрования копий. Сохраните его отдельно от хранилища. Не удаляйте и не пересоздавайте пароль существующего репозитория. Секреты не включаются в Git и архив проекта.

## Проверка и сохранение доказательств

На чистом демонстрационном источнике (до изменения тестовых CSV):

```powershell
py -m pip install -r requirements-dev.txt
py -m unittest discover -s tests -v
py scripts/smoke.py
docker compose ps > evidence/compose-ps.txt
docker compose logs --no-color > evidence/compose.log
```

`smoke.py` проверяет HTTP-авторизацию, создание копии, восстановление, байты трёх файлов и полную целостность репозитория. Если вы уже изменили демонстрационные файлы, их ожидаемые значения в проверке нужно изменить осознанно; не удаляйте реальные данные ради прохождения теста.

Сделайте свои скриншоты: семь работающих сервисов, интерфейс со снимком, завершённое восстановление, результат проверки, состояние кластера и успешный workflow. Не показывайте содержимое `secrets/`.

## Локальная демонстрация Docker Swarm

Для параллельной локальной демонстрации используется отдельный стек backupcluster на порту 8081. У него собственные тома; данные Compose сохраняются.

```powershell
docker swarm init
docker node ls
docker node update --label-add backup.storage=true ИМЯ_УЗЛА_ИЗ_СПИСКА
docker secret create backup_api_token secrets/api_token.txt
docker secret create backup_restic_password secrets/restic_password.txt
$env:IMAGE_PREFIX = 'backupcloud'
$env:IMAGE_TAG = 'local'
docker stack deploy --resolve-image never -c deploy/swarm.local.yaml backupcluster
docker stack services backupcluster
docker stack ps backupcluster
```

Перед этим Compose должен успешно собрать образы `backupcloud/*:local`. Если Swarm уже настроен, повторно `swarm init` не выполняйте. Секрет создаётся только один раз: ошибка «already exists» означает, что нужно использовать существующий секрет, а не менять пароль хранилища. Состояние данных закреплено на единственном узле с меткой `backup.storage=true`; не ставьте эту метку нескольким узлам при локальных томах.

Это одноузловая демонстрация оркестратора, а не доказательство отказоустойчивости между физическими серверами. Для двух и более узлов: подготовьте Linux-ВМ, выполните на втором узле команду присоединения из `docker swarm join-token worker`, используйте доступный всем узлам реестр образов. Разрешите между доверенными узлами порты 2377/TCP, 7946/TCP+UDP, 4789/UDP; они не должны быть открыты всему Интернету. Frontend и proxy запускаются в двух репликах; сервисы с локальными данными закреплены на узле хранения.

Восстановление работы процесса после сбоя и сохранность данных при потере диска — разные задачи. Эта версия не обеспечивает автоматическое переключение локального хранилища при потере узла.

## Kubernetes Docker Desktop: подтверждённый вариант

В Docker Desktop включите Kubernetes с провайдером kind и тремя узлами. В терминале из папки проекта:

```powershell
kubectl --context docker-desktop get nodes
py scripts/deploy_desktop_kubernetes.py
kubectl --context docker-desktop -n backupcloud port-forward service/proxy 8082:80
```

Откройте http://127.0.0.1:8082 и подключитесь токеном из `secrets/api_token.txt`. Терминал port-forward должен оставаться открытым. Ctrl+C прекращает перенаправление порта, приложение в кластере продолжает работать.

Перед развёртыванием должны существовать пять образов `backupcloud/*:local`, redis:7.4-alpine и restic/rest-server:0.14.0. Они получаются при успешном Compose-запуске. Скрипт проверяет три готовых узла, импортирует Linux-образы в containerd каждого узла через временные служебные поды, удаляет их, назначает один storage-узел и применяет манифест. Он требует административного доступа к этому учебному кластеру. Неправильный старый способ `kind load --name desktop` здесь не применяется.

PVC используют StorageClass standard. API и worker разделяют RWO-том восстановлений на одном узле. Политики NetworkPolicy требуют поддерживающего CNI; их принудительное действие в этом стенде отдельно не проверялось.

Для самостоятельного kind вне Docker Desktop также поставляются deploy/kind.yaml и scripts/render_kubernetes.py. Это другой способ подготовки кластера, который не следует смешивать с контекстом docker-desktop.

## GitHub Actions: выполненный CI/CD

Репозиторий: https://github.com/whtluv1337/backup-cloud . Workflow `.github/workflows/ci-cd.yml` запускается при push в main, pull request и вручную. Файлы secrets/, .env и реальные данные в GitHub не загружаются.

- test: 10 модульных тестов, сборка Compose, HTTP-проверка и artifact verification.
- publish: пять собственных образов в GHCR с тегом полного SHA коммита. На pull request публикация не выполняется.
- deploy: отдельная временная Ubuntu-ВМ GitHub-hosted runner, загрузка опубликованных образов, Swarm, секреты, семь сервисов с девятью задачами, полный smoke-тест. Job сохраняет artifact cloud-deployment и очищает стенд.

Доступ к GHCR обеспечивает GITHUB_TOKEN с необходимыми packages permissions. DEPLOY_HOST и SSH-ключи текущему workflow не требуются. Это проверяемый облачный деплой во время CI/CD, постоянный публичный сайт не создаётся.

## Администрирование

- Расписание: `BACKUP_INTERVAL_SECONDS=3600`; `0` отключает периодические копии. Планирование работает только при работающем worker; пропущенные интервалы не воспроизводятся пачкой.
- Один worker: не масштабируйте worker без реализации распределённого блокирования и переработки recovery-семантики.
- Redis: AOF/everysec; при аварии возможна потеря приблизительно последней секунды изменений очереди. Полнота истории не равна сохранности зашифрованного репозитория.
- Незавершённая операция после перезапуска помечается error; администратор проверяет снимки и запускает повтор вручную. Автоматического exactly-once не заявляется.
- После принудительного прерывания restic могут остаться блокировки. Убедитесь, что процессов restic нет, затем вручную выполните `restic unlock` в worker. Автоматическое удаление блокировок запрещено.
- Очистка восстановленных ZIP выполняется администратором после скачивания. Автоматического TTL нет; контролируйте свободное место.
- Удаление старых копий намеренно не вынесено в веб-интерфейс. После согласования регламента хранения применяйте `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --dry-run`; проверьте список и только потом уберите `--dry-run`. `prune` освобождает физическое место и требует отдельной проверки. Это пример политики, не обязательное требование задания.
- `docker compose down` сохраняет тома. `down --volumes` уничтожает данные стенда — не используйте эту команду на рабочем хранилище.
- Для действующей СУБД сначала нужен согласованный dump/снимок средствами СУБД; копирование изменяемых файлов базы не гарантирует логическую согласованность.

## Границы проекта

Стенд демонстрирует частное облачное развёртывание и хранение по REST. Полноценная промышленная система потребует отдельной копии в другом домене отказа, TLS для публичного доступа, ролевой модели, внешнего мониторинга и резервирования очереди/хранилища. В готовой версии доступ администратора по единому токену, один storage-узел и файловый источник. RPO/RTO предприятия без его требований и измерений не гарантируются.
